# HIIT Co. Hub

A mobile-first, installable React + TypeScript member app for HIIT Co., Christchurch. Members sign in with GymMaster to see their own name, total visits and attendance when available. A separate, explicitly selected fictional demo retains staff previews and browser-local training logs. Member workouts come from the published Workout Builder feed; events are managed through the Control Room; Connect supports opt-in member discovery, connection requests and direct messages.

## Run locally

Use Node.js 22.12+ (validated on 24) and npm.

```sh
npm ci
npm run dev
```

Run these commands from the repository root. Vite serves the frontend only; choose the explicit fictional demo from the unavailable-account screen. For member sign-in and API development, run `npm run build` followed by `npm run dev:worker` to serve the app and Worker together. The local Worker has no live GymMaster secret by default. `npm test` runs attendance and demo storage tests. `npm run build` checks TypeScript and builds the production PWA to `dist`. `npm run preview` serves that build. PWA service workers are generated for production builds; use HTTPS when deployed. The existing Cloudflare Worker deploys the `dist` assets and `worker/index.ts` using `wrangler.jsonc`; see `DEPLOYMENT.md` for build/deploy commands and runtime secret setup. A static-only upload to Pages can preview the demo but does not include the backend. Hash navigation allows static hosting without server routes.

## Member accounts

The default experience checks the encrypted GymMaster session and shows member sign-in when needed. Successful login opens a personal Home dashboard; account details and sign-out are available through the avatar. Home and Progress use only the authenticated profile and daily visits, never the demo repository. A failed attendance request leaves real profile totals visible and weekly counts/streaks unavailable. GymMaster support confirmed the prior HTTP 400 was caused by undocumented required `startdate` and `enddate` query fields. Requests include NZ ISO calendar dates, starting with the current and previous 51 weeks. If the confirmed streak reaches that boundary, the server fetches earlier consecutive 52-week windows until the streak ends or history cannot be confirmed. The user has confirmed live attendance now loads; failures never produce fabricated results.

Attendance uses Monday weeks in Pacific/Auckland. The Control Room sets a club-wide weekly training-days target (1–7, default 3). The goal counts distinct NZ dates with a confirmed visit or check-in, so repeat visits on one day count once. Missing dates remain unknown; partial counts show a lower bound. Streaks count consecutive weeks with a confirmed visit, allowing an unfinished current week to preserve the previous week’s streak. The day view shows the current and previous two weeks. The server calculates the current streak using the progressively fetched history without sending extra daily records to the browser; a plus sign marks a lower bound when missing dates or limited history prevent an exact count. Longest/all-time streaks are unavailable. Daily counts cannot supply check-in times; a separate authenticated webhook-record endpoint now provides newly captured NZ arrival times.

Profile and attendance stay in React memory, with no browser storage persistence. Session expiry, sign-out, account changes and refresh failures remove private state. Visibility changes and cross-tab notifications trigger server session revalidation; notification messages contain no identity or credentials. Reload restores only through a valid server cookie. Session lifetimes follow the remembered-session rules below. Signed-in training logs use private account storage; real accounts never read demo exercise records.

## Home workout slate

The fictional demo’s paired-day **This week’s workout** slate uses `src/data/workoutPlan.ts`; the signed-in version uses the published builder feed described below. The three day buttons are Mon/Thurs, Tues/Fri and Wed/Sat, each showing both dates in the current NZ Monday–Sunday week. Each pair uses a single shared station plan so repeated workouts stay identical. Opening a pair shows three stations side by side in a horizontal scroll-snap carousel: 1–3, then 4–6, then 7–9. Each station is a three-minute round. Members can swipe, use previous/next arrows, choose a group, or focus the carousel and use keyboard left/right arrows. Switching pairs resets to Stations 1–3. Each station has its own exercises and instructions. Trackable exercise names link to the matching Log detail through routes such as `#log/back-squat`; these links also survive reloads. Non-trackable movements remain plain text. These are explicitly labelled sample station workouts, not the gym’s published programme. Published plans for signed-in members are managed in the separate Workout Builder. Upcoming club events appear above the Skills Library button.

## Training log

The **Log** pencil tab opens an exercise list. Choose a preset such as Back squat, or add a custom exercise. Record a workout date and up to 50 sets, each with reps and total weight in kilograms (including the bar). Dates cannot be in the future. Zero kilograms represents bodyweight-only work: the volume metric counts added load only. Entries begin empty; no training results are invented.

Opening an exercise shows its heaviest recorded set, latest session volume, weight and volume charts, and dated session history. Chart **Weight** means the heaviest set in each session; **Volume** means the sum of reps × kg across all that session's sets. Charts show the latest 12 sessions, ordered by workout date and then creation time, with points spaced by session. Multiple sessions on the same day are retained separately. Changes compare the earliest and latest saved session, not personal bests. Full recorded sets remain in history. Sessions can be edited and deleted with confirmation; the charts recalculate immediately.

`src/domain/training.ts` defines and tests validation and calculation rules. `src/data/training.ts` handles versioned browser localStorage per demo member. Custom exercises, sessions and corrections survive reloads on the same browser; they do not sync to other devices. Demo member separation is not authentication or secure access control. Storage errors leave existing history untouched and retain unsaved form input. Unreadable data is not silently reset. Signed-in members use the separate encrypted account backend described below; demo records are never automatically imported.

## Attendance rules

Weeks run Monday–Sunday in Pacific/Auckland, including NZ daylight saving. A workout is a distinct attendance event, not an app login. Duplicate event IDs, invalid dates, future events and other members' visits are excluded. Multiple legitimate visits on one day count individually, with a single calendar indicator. A streak counts consecutive weeks with at least one visit; an empty current week does not break the preceding streak until that week has ended. Longest streak is shown only when history is complete. Milestones are 50, 75, 100, 150, 200, then every 100 visits. Goal percentages can exceed 100%; the circular indicator fills to 100%. The six-week chart's target line represents the current target, not reconstructed historical targets.

## Backend and GymMaster member connection

`worker/index.ts` serves the static app and uncached JSON routes under `/api`. `GET /api/health` returns only `{"status":"ok"}`. The default sign-in screen accepts an authorised member’s GymMaster email/password using the runtime `GYMMASTER_API_KEY` **Secret**. Worker code validates the documented login response and stores only an encrypted, HttpOnly/Secure session cookie. Passwords are not persisted or logged; the raw token and key are not returned to browser JavaScript. Same-origin checks, bounded request/response bodies and a Cloudflare rate-limit binding protect the login route. The connection expires according to the provider's expiry, capped at one hour, and can be disconnected.

The member Home and Progress screens use `GET /api/gymmaster/profile` and `GET /api/gymmaster/visits`. Profile returns first name, surname and total visits only after matching the provider member ID to the encrypted session. Attendance returns documented daily counts for three weeks, without inferring timestamps or filling missing days with zero. The user has confirmed deployed sign-in and profile totals; the missing date parameters behind the daily-attendance HTTP 400 are now supplied, pending live verification. Automated backend and browser checks use fake credentials and mocked responses. Other unimplemented GymMaster routes remain 501; unknown API routes return 404. Staff previews expose fictional data only. Never supply credentials or keys in chat. See `DEPLOYMENT.md`.

## Check-in webhook preparation

A token-authenticated webhook receiver and private encrypted SQLite Durable Object inbox are implemented at `/api/gymmaster/webhooks/checkin`. Configure the same private Secret Token in GymMaster and the runtime `GYMMASTER_WEBHOOK_TOKEN` secret; the deployment creates the inbox binding. Authentication, duplicate protection, test/live separation and 30-day staging retention are implemented. The observed `member_checkin` payload is mapped only when `access` is `granted`, it has a valid member/visit ID and NZ local `payload.timestamp`, and neither test flag is true. The user confirmed these wall times are NZ time. Each member can read only their own recent times through the authenticated session. Webhooks do not change daily counts or fabricate historical visit times. See `DEPLOYMENT.md` for setup and testing.

## Member arrival times

Tapping an attendance day on Home or Progress shows real arrival times, door names and GymMaster visit references from non-test granted check-in webhooks. Timezone-less `payload.timestamp` is preserved as a Pacific/Auckland wall time, as confirmed by the user, rather than replaced by the webhook envelope/delivery timestamp or shifted by another 12/13 hours. Counts and streaks remain sourced from the daily API, so webhook receipt cannot inflate them. A received timestamp can mark a day even before the daily count updates.

`GET /api/gymmaster/checkins` derives the identity from the encrypted session cookie. It queries a secret-HMAC member index in the existing private SQLite Durable Object, decrypts records using member-bound authenticated encryption and returns only ID/date/local time/door for the current and previous two NZ weeks. Raw member IDs/names are not returned. Tests, denied attempts, malformed and unknown event types are not mapped. Duplicate event/visit IDs do not duplicate arrivals. Profile, counts and arrival-time failures are handled separately; sign-out/account changes clear times from memory.

Retained authenticated staging events are automatically reprocessed in batches of 50, excluding tests and denied attempts. Explicit UTC/offset timestamps are converted to NZ local time; timezone-less values remain NZ wall times. Visits without a delivered webhook still have no arrival time. Arrival records expire after 30 days, and history in the day view remains three weeks. No new Cloudflare binding or secret is required. Changing the webhook token changes the encrypted-record key and member index, so migrate retained records first if continuity is required.


Member home now places the unboxed total visit count beside the greeting. Its button reveals weekly goal, streak and milestone cards; the default view leads with the expanded workout plan for today's NZ weekday. Mon/Thurs, Tues/Fri and Wed/Sat repeat; Sunday opens the latest Wed/Sat plan. Workout selectors are compact and the three-station carousel remains available.

The login form offers an unchecked “Keep me logged in” checkbox. Without opt-in, the encrypted HttpOnly cookie has no Max-Age and the server session lasts at most one hour. With opt-in, the cookie persists for the shorter of GymMaster's returned token lifetime and seven days. It uses a fixed upstream host without forwarding member credentials. The current NZ week's three day pairs are requested independently; only the builder's approved published content is shown. Draft/missing workouts and conflicting schedules have distinct messages and never fall back to demo plans. Station text preserves line breaks, CHOW labels and the three-station carousel. The separate fictional demo still uses sample plans.

In the builder, set the block dates, choose the program week, save changes, then **Publish week**. Members reopen Home or refresh attendance to load the latest published plan. Editing approved content makes that plan unavailable until republished, according to the builder's existing feed rules. Sunday displays the latest Wed/Sat pair. No builder source changes are required.

Known unambiguous exercise names link directly to their account log. Stations 2, 3, 7 and 8 link recognised exercise names inline; stations 1, 4, 5, 6 and 9 have no logging links. Members can also use Log to add custom exercises; variants are not automatically merged into unrelated lift histories. Reps, sets, kg, session dates, weight/volume charts and edit/delete are available to signed-in members.

Account logs use authenticated `GET/POST /api/gymmaster/training` and the private SQLite Durable Object `MemberTrainingStore`. The `MEMBER_TRAINING_LOGS` binding/migration is provisioned by normal Wrangler deployment. Identity comes only from the encrypted session; stored indexes are HMAC-derived and log contents AES-GCM encrypted with member-bound associated data using the runtime API key. Rotating that key changes indexes/encryption keys: migrate account logs before rotation to preserve access. No credentials, records or member identifiers are added to browser storage or logs. Revision checks reject stale writes rather than silently overwrite another device's changes. Existing demo localStorage is never used for an authenticated account. Logs are bounded to 200 exercises, 1,000 sessions and 50 sets per session.


The production app now reaches the builder through Cloudflare service binding `WORKOUT_BUILDER` (service `hiit-co-workout-builder`), preserving the fixed read-only endpoint. Public HTTPS remains a fallback for local configurations without the binding. Only a dated JSON `No published workout for this date` response is treated as unpublished; edge/router HTML or unrelated 404s are connection errors. The UI shows the requested week/date pair and safe connection code, so a routing failure cannot masquerade as an unpublished plan. Logs contain fixed `WORKOUT-*` stages and dates, without credentials or workout text. The user confirmed the live public builder feed returns the nine-station Strength Week 1 plan for 26 October 2026. The direct service link was verified locally with two real Workers, but the deployed app still requires confirmation after rollout.


Inline workout logging preserves the published instructions and links only the exercise-name spans, including common builder abbreviations such as DB Box Step ups and SA Row. A shared movement catalog supplies stable IDs across changes in reps, day labels and text case; equipment variants keep separate histories. The selected exercise form opens directly, preparing a new exercise in memory only when needed and persisting it with the first saved session. Existing matching custom names reuse their IDs/history. ### Connect

The last navigation tab is **Connect** (`#connect`; old `#messages` links redirect). Every member starts Private. Members become discoverable only after enabling **Make my profile public**. Discovery shares names only with signed-in members, never GymMaster IDs, emails, visits or strength data. Private members may initiate a request to a public member. Pending requests can be accepted, declined or cancelled; only the recipient can accept. Accepted connections can message even after either member returns to Private. Disconnecting or blocking removes the relationship and stored conversation for both members. Blocking prevents discovery, new requests, sends and history access in both directions; unblocking restores none of these automatically.

`/api/gymmaster/connect` derives the actor from the encrypted GymMaster cookie, rejects cross-site reads and foreign-origin writes, validates bounded text bodies and never accepts caller-supplied member identity. The existing private ControlStore binding persists profiles (default `public=0`), relationships, blocks and messages in indexed SQLite tables; no new binding or secret is required. Connect IDs use a separate HMAC namespace. Names and message text are encrypted with purpose/pair-bound AAD; they are not end-to-end encrypted. All messaging checks and relationship changes execute together in the private store. Text messages are limited to 2,000 characters, recent histories return 50 messages with cursor pagination, and retry IDs prevent duplicate sends. Per-member limits cover reads (90/minute), requests (5/minute) and other writes (30/minute).

Connect polls the directory/requests every 15 seconds and the open conversation every 10 seconds while visible. It refreshes on returning to the app. This release does not include background push notifications, media attachments or group chats. Existing members need to open Connect and opt in before appearing in discovery. Run `npm run test:connect` for real Worker/SQLite tests of privacy, consent, isolation, persistence, blocking, pagination and rate limits. The fictional demo does not send real requests or messages.
